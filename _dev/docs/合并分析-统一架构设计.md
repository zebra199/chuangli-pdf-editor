# 统一功能架构设计：图片 + PDF 混合编辑器

> 依据：`合并分析-参考项目审计.md`、`合并分析-编辑器审计.md`
> 结论：深度融合可行，核心是给「页面流」条目引入 `kind` 维度。

---

## 一、统一数据模型（深度融合方案）

```js
state = {
  files: [{
    id, name, size, color, kind: 'pdf' | 'image',
    pageCount,                 // 贡献的页数
    bytes,                     // pdf: ArrayBuffer 副本；image: null
    // 图片文件额外字段：
    bitmap,                    // ImageBitmap / HTMLImageElement（原始方向，已 EXIF 纠正）
    natW, natH,                // 原始像素尺寸
    heic, proxyBytes,          // HEIC 标记 / 编码体积估计
    ok, error                  // 图片解码状态
  }],

  pages: [{                    // ★ 统一页面流：顺序即导出顺序
    uid, fileId, fileName, srcNo,
    kind: 'pdf' | 'image',     // ★ 新增：页面类型
    w, h,                      // 逻辑尺寸(pt)：pdf=源页 pt；image=按设置算出的页尺寸
    rot, hMirror, vMirror,     // 编辑操作清单（两类通用）
    err, displayThumb
  }],

  selected: Set<uid>, history: [], future: [],
  fileSeq, pageSeq, anchorUid, dragUid, thumbCache,
  // ★ 新增：图片页设置（移植自参考项目）
  imgSettings: { paper:'A4', orient:'auto', enhance:'none', fit:'contain', dpi:200 },
  // 原有：导出压缩档位
  compress: 'none' | 'low' | 'medium' | 'high'
}
```

**设计要点**：
- 图片文件 = 一页（`kind:'image'`，`srcNo` 恒为 1）；PDF 文件 = 多页（`kind:'pdf'`）
- 编辑操作（旋转/镜像/删除/拖拽/撤销重做）**对两类页面完全通用**，不需分支
- 图片位图存 `files[].bitmap`（不重复存到 pages），页面通过 `fileId` 引用
- 混合流允许图片与 PDF 任意穿插排序

## 二、统一导入链路

```
addFiles(fileList)                      // ★ 单一入口，按类型分流
  ├ 扩展名 .pdf / type=application/pdf → addPdfFile(f)   （现有逻辑）
  └ 扩展名 图片 / type=image/*          → addImageFile(f) （移植参考项目）
       ├ HEIC/HEIF → heic2any 转 JPEG
       ├ createImageBitmap({imageOrientation:'from-image'})   // EXIF 纠正
       ├ bitmap/natW/natH/ok/error 记录
       └ pages.push({ kind:'image', w:imgSettings.pageW, h:imgSettings.pageH, ... })
```

- 拖放 / 选择框 `accept` 扩展为 `.pdf,image/*`（含 .heic/.heif）
- 图片文件走「一文件一页」；PDF 走「一文件多页」
- 图片导入后可**异步解码**（先占位卡片，解码完更新缩略图），保持大图批量导入流畅

## 三、统一渲染（缩略图）

| 页面类型 | 缩略图来源 | 变换 |
|---|---|---|
| PDF 页 | `thumbCache[uid]`（pdf.js 渲染） | canvas 按 rot/hMirror/vMirror 变换 |
| 图片页 | `bitmap` 直接缩放绘制 | 同上（同一套 `makeThumbFromOps` 逻辑，按 kind 取源图） |

**统一为**：`makeThumbFromOps(page)` 内部按 `kind` 决定源图（thumbCache 位图 or image bitmap），后续变换代码共用。

- 分组头：PDF 文件按文件分组显示；图片文件可选「各自独立组」或「合并为一个『图片』组」→ **推荐各自独立组**（保留文件名便于识别）
- 徽标：统一显示全局导出序号（与现有一致）

## 四、统一导出管线

```
doExport()
  根据 compress + 每页 kind 决定每页处理方式
  ┌ PDF 页
  │   compress='none' 且无镜像 → pdf-lib copyPages + /Rotate（矢量保真）
  │   有镜像 或 compress≠'none' → pdf.js 渲染 → canvas 变换 → JPEG → embedJpg
  └ 图片页（无论如何都转图）
      planForImage(page) → 目标页尺寸 + 栅格像素 + 摆放
      → 白底 → 旋转 → 缩放 → 白底增强 → JPEG(档位质量或 DPI 对应质量)
      → embedJpg → addPage([pageW, pageH]) + drawImage
```

**画质双轨的处理（关键设计决策）**：
- 图片页：受「图片设置」的 DPI 控制（150/200/300），**同时**可选择是否套用压缩档位的质量系数
- 简化方案（推荐）：**图片页质量 = 图片设置里的 DPI 决定**；压缩档位**只作用于 PDF 页**。UI 上分区说明，避免用户困惑。
- 备选方案：压缩档位全局统一作用于所有页（图片页的 DPI 仅决定像素数，质量跟档位）。→ 更统一但会让高压缩把清晰照片压糊。

## 五、统一界面布局

```
┌─ 标题栏：📄 PDF 编辑器（合并版）  纯本地运行 · 支持 PDF 与图片
├─ 设置区（两张卡片）
│   ├─ 卡片1「图片设置」（仅当有图片页时可用/高亮）
│   │    纸张 A4/A5 · 方向 · 白底增强 · 适配 · DPI
│   └─ 卡片2「导出压缩」（作用于 PDF 页）
│        不压缩/低/中/高 + 体积预估
├─ 导入区：拖入 PDF 或图片（JPG/PNG/HEIC）
├─ 编辑工具条：⟳旋转 ⇋水平镜像 ↕垂直镜像 🗑删除 ↺撤销 ↻重做
├─ 页面网格：混合卡片流（PDF 页 + 图片页），分组头、拖拽排序
└─ 底栏：状态信息 + 清空 + 生成 PDF（绿色主按钮）
```

- 沿用现有 CSS 变量与组件，视觉零割裂
- 「图片设置」卡片在无图片页时显示但置灰（或折叠），有图片页时启用

## 六、两个方案对比

### 方案 A：深度融合（单一工具，混合页面流）

| 维度 | 评价 |
|---|---|
| 用户体验 | ⭐⭐⭐⭐⭐ 一个工具搞定「图片→PDF」与「PDF 编辑」，图片与 PDF 可混排，能力最强 |
| 代码复用 | 复用约 60%+，新增图片模块（planFor/renderCanvas/白底增强/heic2any） |
| 工作量 | **中等偏大**：约 10 处改造点（kind 分流、导入/渲染/导出三分支、设置分区、预估、撤销适配、heic2any 内嵌） |
| 风险 | 画质双轨可能让用户困惑（需 UI 说明）；混合流的边界（图片页尺寸 vs PDF 页尺寸）需设计清楚 |
| 单文件体积 | 约 3.7MB（新增 heic2any 1.3MB） |
| 交付物 | 1 个 HTML |

**优点**：能力最强、交互统一、无需用户理解"两个工具"的概念
**缺点**：改造面广、验证工作量大、体积增大

### 方案 B：双入口（一个工具，两个功能区）

| 维度 | 评价 |
|---|---|
| 用户体验 | ⭐⭐⭐ 顶部 Tab 切换「PDF 编辑」/「图片转 PDF」，各自独立工作流 |
| 代码复用 | 同源 CSS/组件复用；两套页面流可**各自独立**（互不干扰），几乎零耦合改造 |
| 工作量 | **小**：把参考项目逻辑整体移植为第二个功能区，共用 CSS/预览/进度/toast/构建脚本 |
| 风险 | 低。两个功能区互不影响，回归风险小 |
| 单文件体积 | 约 3.7MB（同样内嵌 heic2any） |
| 交付物 | 1 个 HTML（含 Tab） |

**优点**：改造小、风险低、两个成熟工具各自保留完整能力、UI 清晰（用户明确知道自己在做什么）
**缺点**：不能「图片与 PDF 混排」（如：几页照片 + 一份 PDF 合并成一个文件）——这是最大能力差异

### 方案 C（补充）：深度融合 + 保留独立入口（折中）

单页面流支持混合，**同时在设置区提供「快捷模式」**：一键清空并切换到纯图片/纯 PDF 场景。
- 相当于方案 A 的能力 + 方案 B 的心智模型
- 工作量略高于 A（多一层模式提示），但体验最好

## 七、推荐结论

**推荐方案 A（深度融合）**，理由：

1. **用户真实需求指向混合**：「把合同照片和一份 PDF 合成一个文件」是常见场景，只有深度融合能做到
2. **架构同构度高**：页面流模型天然兼容，改造是「加一个维度」而非「重写」
3. **pdf-lib 版本一致 + CSS 同源**：技术风险低
4. **交互统一**：选中式批量工具条比参考项目的单卡按钮更强，用户学习成本低

**若你更看重稳妥/快速**，则选方案 B（双入口）——改造最小，两个工具各自完整，代价是不能混排。

**工作量估算（方案 A）**：
| 步骤 | 内容 |
|---|---|
| 1 | 数据模型加 kind + imgSettings；导入分流 addImageFile |
| 2 | 缩略图/卡片渲染按 kind 分支 |
| 3 | 移植 planFor / renderCanvas / enhanceCanvas |
| 4 | 导出管线加图片页分支 |
| 5 | 设置面板加「图片设置」卡片 |
| 6 | 体积预估分类型 |
| 7 | 内嵌 heic2any + 重新构建单文件 |
| 8 | 全功能验证（图片、PDF、混合、四档压缩、HEIC） |

**待你确认的点**：
1. 选 **A（深度融合）** 还是 **B（双入口）**？（我推荐 A）
2. 画质双轨怎么处理：**图片页用 DPI、PDF 页用压缩档位**（推荐）还是全局统一？
3. 图片设置面板：**常驻显示**还是**仅有图片页时展开**？
